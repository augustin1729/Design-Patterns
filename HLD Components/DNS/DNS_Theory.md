# **System Design — Domain Name System (DNS)**

# **1\. What It Is & Why It Exists**

* **Core Purpose:** The internet's phonebook. Humans remember hostnames (`example.com`); network routing hardware requires IP addresses (`93.184.216.34` or IPv6).  
* **Protocol & Port:** Runs primarily on **UDP Port 53** for low latency (no 3-way TCP handshake). Automatically falls back to **TCP Port 53** if data exceeds size limits (512 bytes legacy, or extended via EDNS0) or during zone transfers (AXFR).

# **2\. The Resolution Hierarchy (Top-Down)**

When an IP is not cached, the lookup moves strictly **from the root downward**:

1. **Client / Stub Resolver:** Your device (browser / OS) queries the local recursive resolver.  
2. **Recursive Resolver:** The intermediate server (ISP, Google `8.8.8.8`, Cloudflare `1.1.1.1`) does the multi-step lookup:  
   * **Root Nameserver (`.`):** Knows where Top-Level Domains live (points to `.com` TLD servers).  
   * **TLD Nameserver (`.com`):** Knows who manages the domain (points to the domain's authoritative nameservers).  
   * **Authoritative Nameserver:** The source of truth configured by the domain owner; returns the final IP.  
3. **Recursive Resolver caches the answer** and returns it to your device.

# **3\. The Multi-Layer Caching Stack**

Queries check these layers in sequence before contacting external nameservers:

* **Browser Cache:** Short-lived internal DNS table in Chrome/Firefox.  
* **Operating System Cache:** Local OS daemon (e.g., `systemd-resolved` on Linux, DNS Client service on Windows).  
* **Local Gateway / Router:** Caching resolver running on the local network router.  
* **Recursive Resolver Cache:** Upstream ISP or public DNS provider cache.

# **4\. Essential Record Types**

| Record Type | Description |
| :---- | :---- |
| **A** | Maps hostname to **IPv4** address. |
| **AAAA** | Maps hostname to **IPv6** address. |
| **CNAME** | Canonical Name (alias). Points one domain name to another (cannot be set at the root/apex domain `example.com`). |
| **NS** | Nameserver record. Specifies which authoritative servers manage the zone. |
| **MX** | Mail Exchange. Directs email traffic to the target mail servers with priority order. |
| **TXT** | Arbitrary text data, heavily used for ownership verification, SPF, and DKIM. |

# **5\. TTL (Time to Live)**

* **High TTL (e.g., 24 hours):** Maximizes caching, minimizes lookup overhead and server load, but delays propagation during IP changes or disaster recovery.  
* **Low TTL (e.g., 60–300s):** Fast updates and swift failover, but generates higher query volume and latency on cold lookups.

# **6\. DNS Packet Anatomy & Binary Wire Decoding**

## **The 12-Byte Fixed Header**

Every standard DNS packet begins with an identical 12-byte header, split into six 16-bit (2-byte) big-endian integers:

* **Transaction ID (Bytes 0–1):** A random 16-bit identifier generated by the client (e.g., 0xAABB / 43707). Stateless UDP does not maintain a persistent connection; this ID allows the operating system/socket to correlate an incoming asynchronous reply to the exact question asked.  
* **Flags (Bytes 2–3, 16 bits):**  
  * **Bit 15 (QR):** 0 \= Query, 1 \= Response.  
  * **Bits 14–11 (Opcode):** 0000 for standard query.  
  * **Bit 10 (AA):** Authoritative Answer. Set to 1 by nameservers that own the zone; set to 0 by caching resolvers (like 8.8.8.8).  
  * **Bit 9 (TC):** Truncation. Set to 1 if the payload exceeds UDP MTU limits (512 bytes legacy), instructing the client to retry over TCP Port 53\.  
  * **Bit 8 (RD):** Recursion Desired. Set by the client asking the resolver to chase down the IP recursively across Root, TLD, and Authoritative servers.  
  * **Bit 7 (RA):** Recursion Available. Set by the resolver confirming it supports full recursive lookups.  
  * **Bits 3–0 (RCODE):** Return Code (0 \= NOERROR, 3 \= NXDOMAIN / domain does not exist).  
* **Section Counters (Bytes 4–11):** Four 16-bit fields indicating record counts:  
  * **QDCOUNT:** Question count (typically 1).  
  * **ANCOUNT:** Answer records returned.  
  * **NSCOUNT:** Authority records returned.  
  * **ARCOUNT:** Additional records returned.

## **Payload Encoding & Compression Pointers**

* **QNAME Encoding:** Domain names avoid raw dot notation. They are encoded as length-prefixed chunks (labels) followed by a null terminator byte (0x00). Example for google.com: \\x06google\\x03com\\x00 (6 bytes of google, 3 bytes of com, ending in 0x00).  
* **Message Compression Pointers (0xC0):** To avoid duplicating long domain strings across multiple Answer/Authority sections in constrained UDP packets, DNS uses pointers. A 2-byte sequence starting with binary 11xxxxxx (hex 0xC0) tells the parser: "Do not look for ASCII characters here; interpret the remaining 14 bits as a byte offset from the start of the packet where this domain string was already spelled out." (e.g., 0xC00C points back to byte offset 12).  
* **Resource Record Wire Structure:** Every answer entry follows: Name (Pointer/Label) \-\> Type (2B) \-\> Class (2B) \-\> TTL (4B) \-\> RDLENGTH (2B) \-\> RDATA (Variable, 4B for IPv4)

# **7\. Networking Foundations: IPs, Subnets & CIDR Calculation**

## **The Core Problem & Subnet Masks**

* **IPv4 Structure:** 32 bits divided into four 8-bit octets (values 0 to 255).  
* **Role of the Subnet Mask:** An IP address conveys two pieces of information: the Network ID (the logical neighborhood) and the Host ID (the individual machine). The subnet mask is a continuous string of binary 1s (network portion) followed by 0s (host portion) that determines where the boundary lies.  
* **Local vs. Routed Decisions:** When a device sends traffic, it applies a bitwise AND between the destination IP and its own subnet mask:  
  * If the resulting Network ID matches its own, the destination is local (Layer 2 ARP/Wi-Fi frame directly to the machine's MAC address).  
  * If the Network ID differs, the device forwards the packet to its Default Gateway (router).

## **Deconstructing a Custom Mask (e.g., 255.255.248.0 / /21)**

* **255.255.248.0 in binary:** 11111111 . 11111111 . 11111000 . 00000000 (8+8+5=21 ones → /21).  
* **Host Bits:** Remaining zeros \= 3 (3rd octet) \+ 8 (4th octet) \= 11 bits.  
* **Capacity:** 2^11 \= 2,048 total addresses in the subnet.  
* **Why 10.40.29.215 and 10.40.24.1 are on the same subnet:**  
  * Gateway 3rd octet (24): 0 0 0 1 1 0 0 0  
  * Laptop 3rd octet (29): 0 0 0 1 1 1 0 1  
  * Subnet mask 3rd octet (248): 1 1 1 1 1 0 0 0  
  * The first 5 bits (0 0 0 1 1\) are identical. Because all 21 network bits match, both devices sit on the same local subnet (10.40.24.0 to 10.40.31.255) and communicate directly without traversing a router.

## **Calculating Subnet Ranges from Scratch (e.g., finding the subnet for 10.20.35.130/26)**

4. **Host bits:** Total 32 bits; 32 \- 26 \= 6 host bits.  
5. **Block / Step size:** 2^6 \= 64\. Subnets increment in multiples of 64 in the 4th octet.  
6. **Step boundaries:**  
   * Block 1: .0 to .63 (10.20.35.0/26)  
   * Block 2: .64 to .127 (10.20.35.64/26)  
   * Block 3: .128 to .191 (10.20.35.128/26)  
   * Block 4: .192 to .255 (10.20.35.192/26)  
7. **Locating the IP:** 130 falls between 128 and 191\.  
   * **Subnet ID:** 10.20.35.128/26  
   * **Usable Host Range:** 10.20.35.129 through 10.20.35.190  
   * **Broadcast Address:** 10.20.35.191

# **8\. DNS Traffic Routing & Infrastructure Mechanics**

## **Round-Robin DNS (RR-DNS) & Its Failures**

* **Mechanism:** The nameserver rotates the order of multiple A records cyclically per query so clients pick different IPs.  
* **Why it falls apart in production:**  
  * **No Load Feedback:** It routes equally to an overloaded server and an idle one.  
  * **Sticky ISP Caching Skew:** If an ISP or corporate proxy caching resolver fetches an IP, all thousands of downstream users behind that ISP are pinned to that single backend until the TTL expires.  
  * **Failover Blindness:** If a backend machine dies, the DNS server continues handing out its dead IP until health checks update the record and downstream caches expire.

## **Geo-DNS & EDNS Client Subnet (ECS / RFC 7871\)**

* **The Problem:** Authoritative nameservers only see the IP address of the Recursive Resolver contacting them, not the end user. If a user in India queries via an Anycast resolver exit node located in Europe, standard Geo-DNS might mistakenly serve a European data center IP.  
* **The ECS Solution:** The recursive resolver appends an EDNS extension containing an anonymized slice of the client's actual IP subnet (typically the /24 prefix). The authoritative nameserver reads this prefix to pinpoint the user's geographic region and returns the lowest-latency edge server.

## **Anycast BGP vs. Unicast DNS**

* **Unicast:** One IP address maps to one physical network card. If that server fails or floods, the IP becomes unreachable.  
* **Anycast:** The exact same IP address (e.g., 8.8.8.8 or 1.1.1.1) is advertised simultaneously across hundreds of global data centers via BGP (Border Gateway Protocol).  
* **Operational Benefits:**  
  * Internet routers automatically route client UDP packets along the shortest autonomous system path (fewest network hops).  
  * **Inherent DDoS absorption:** A volumetric attack is naturally fragmented and absorbed across hundreds of distributed edge PoPs rather than concentrating on a single target.  
  * **Instant failover:** If a data center drops, its BGP route advertisement is withdrawn, and adjacent internet routers immediately redirect subsequent packets to the next closest healthy site.

## **Architectural Boundary: DNS vs. Reverse Proxies / Load Balancers**

* **DNS Level:** Macro-level, cross-region traffic steering (routing users to the nearest AWS region or global CDN edge). Inherently coarse and delayed by TTL caching.

**Load Balancer Level (L4/L7 like HAProxy, NGINX, ALB):** Micro-level, sub-second routing within the data center. Directly monitors socket connections, server health, CPU load, and session stickiness in real time.
